# v0.13 — Player navigation pilot

Status: planned; implementation not started in the supplied archive.
Goal: a visible placeholder player walks on one authored single-screen 2D floor
using held arrow keys and ground clicks, with credible obstacle handling.

## Entry conditions

- v0.12 player-facing save/load is accepted; its focused audit is complete or explicitly skipped.
- The feature branch includes current main and passes its real-dependency checks.
- Choose a representative existing scene and resolve OPEN-03/04/05 in [decisions](../decisions.md).
- Keep the original puzzle rules and logical 1280 x 720 display contract.

## D130-01 — Prove scene navigation data

- [ ] Choose Village Square or Forest Path and document the pilot floor/obstacle layout.
- [ ] Define a safe default foot-position spawn and facing.
- [ ] Separate floor, blockers/actor footprint, click bounds, and artwork bounds.
- [ ] Exclude UI-occupied space from world movement input and navigation.
- [ ] Select the smallest representation/routing approach that proves a detour around one blocker.
- [ ] Define unreachable/outside-floor click feedback; do not silently teleport.

Done when: keyboard and click travel can be checked against one explicit traversable
area; a reachable test destination requires a real detour and an unreachable one
has a defined outcome. No camera or general map editor is needed.

## D130-02 — Visible player and held-arrow movement

- [ ] Add minimal session-owned position and facing with a placeholder sprite/shape.
- [ ] Move from held semantic directions using delta_time, not repeated KEYDOWN steps.
- [ ] Normalize diagonal input so it is not faster than cardinal input.
- [ ] Apply the common footprint/floor/blocker policy and collision-safe stepping.
- [ ] Bound large-frame-time behavior to prevent tunnelling or post-focus teleports.
- [ ] Reconcile arrow/menu actions by context and derive Controls labels from real bindings.
- [ ] Clear held input on focus loss and session replacement.

Done when: held arrows move at consistent speed without escaping the floor or
crossing blockers; opening a modal surface cannot leave stuck movement.

## D130-03 — Click-to-move

- [ ] Convert physical pointer positions through DisplayViewport only once.
- [ ] Ignore inventory/menu/dialogue input and letterbox clicks as world destinations.
- [ ] Route ground clicks through the same navigation policy used by arrows.
- [ ] Follow a bounded route, stop without oscillation, and handle already-at-destination.
- [ ] Replace automatic travel predictably when another movement command arrives.
- [ ] Give clear feedback for rejected or unreachable destinations.

Done when: the actor reaches a ground destination and routes around the pilot
obstacle; neither route following nor its failure moves through blocked space.

## D130-04 — Modal and presentation integration

- [ ] Apply the confirmed cancellation policy when pause/dialogue/Controls opens.
- [ ] Keep Escape's accepted modal order; do not add a conflicting movement-cancel layer.
- [ ] F11/scaling preserve logical position, facing, and live session state.
- [ ] Document temporary direct-click interactions and positionless save behavior in
  this one-scene development pilot; v0.14 replaces them before full movement release.
- [ ] Keep non-pilot scenes and the original demo tests usable.

## D130-05 — Verify the pilot

- [ ] Automated: cardinal/diagonal speed, frame partitioning within tolerance,
  collision/blocker detour, unreachable destination, replacement/cancellation,
  focus-loss clearing, no movement under UI/modal input, and output-coordinate conversion.
- [ ] Desktop: arrows and clicks feel responsive, feet stay on the floor, paths are
  understandable, UI does not steal unintended world movement, fullscreen remains correct.
- [ ] Run format/lint/full pytest with real Pygame and preserve branch-specific results.
- [ ] Record actual limitations and only implemented architecture changes.

## Acceptance and non-goals

One scene proves both control methods and one genuine obstacle detour. Placeholder
art is sufficient; no skeletal/animation system, scene editor, camera, autosave,
extra content, or universal pathfinding library is required. The exact speed and
arrival tolerance are tuned in the pilot. This milestone is not the full-demo
proximity or movement-save release; those are explicit v0.14 dependencies.
