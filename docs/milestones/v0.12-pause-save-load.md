# v0.12 Task List — Pause, Save/Load, and Menu Foundation

Status: planned
Goal: save and restore the complete current demo through clear title, pause, confirmation, and ending flows.

## Working rule

Complete one task ID at a time. For each task:

```txt
1. discuss unresolved decisions
2. inspect existing tests and ownership
3. implement only the active task
4. add focused tests
5. run formatting, lint, focused tests, and the full suite when possible
6. leave manual checks open until confirmed
7. update this file with implemented facts only
8. commit before starting the next task
```

Do not implement v0.12.1 cleanup while feature behavior is still changing.

## Approved milestone decisions

- [x] Use one manual save slot during v0.12.
- [x] Defer autosave until a larger content milestone provides meaningful authored checkpoints.
- [x] Use `platformdirs` for an operating-system user-data directory.
- [x] Keep gameplay saves separate from future settings/configuration data.
- [x] Use a versioned save-file envelope around the existing state snapshot.
- [x] Write the manual save atomically and preserve the previous valid file on failure.
- [x] Title menu: New Game, Continue when valid, Controls, Exit.
- [x] Pause menu: Resume, Save Game, Load Game, Controls, Return to Title, Exit Game.
- [x] Ending menu: Title Menu and Exit Game.
- [x] Remove the global `N` shortcut and player-facing binding.
- [x] `Escape` must never quit the application directly.
- [x] Gameplay `Escape` closes dialogue, then clears inventory selection, then opens pause.
- [x] Paused `Escape` resumes gameplay.
- [x] `F11` remains global and presentation-only.
- [x] Loading a completed snapshot enters ending mode immediately over the restored scene.
- [x] Restore persistent snapshot facts and clear transient presentation/menu state.
- [x] Use concrete pause/confirmation screen objects; `GameApp` owns navigation and application actions.
- [x] Do not introduce a general screen framework during v0.12.

## D120-04 — Define the save-file envelope and status model

- [ ] Define save-file format version 1 separately from the existing snapshot version.
- [ ] Wrap the snapshot in a plain JSON-compatible envelope containing at minimum the file version, UTC save timestamp, and snapshot payload.
- [ ] Validate envelope shape and types before calling snapshot restoration.
- [ ] Distinguish missing, valid, invalid JSON, invalid envelope, unsupported file version, invalid snapshot, and unreadable-file outcomes.
- [ ] Keep raw filesystem/JSON exceptions from leaking into player-facing menu code.
- [ ] Do not implement migrations; unsupported versions fail safely and clearly.
- [ ] Add focused envelope, timestamp, status, and unsupported-version tests.

Recommended shape:

```json
{
  "save_format_version": 1,
  "saved_at_utc": "<ISO-8601 UTC timestamp>",
  "snapshot": {}
}
```

Exit condition:

```txt
One plain save format can be validated without constructing or mutating a game session.
```

## D120-05 — Implement atomic manual-save I/O

- [ ] Serialize the envelope as UTF-8 JSON.
- [ ] Create the user-data directory only when a write requires it.
- [ ] Write a temporary file in the same directory as the final save.
- [ ] Flush the completed temporary file and sync it where supported.
- [ ] Replace the final save with `os.replace()` only after the temporary write succeeds.
- [ ] Clean up temporary files after handled failures where practical.
- [ ] Preserve the previous valid manual save when writing, flushing, syncing, or replacing fails.
- [ ] Return typed/domain-level failure information suitable for UI messages.
- [ ] Add tests for successful writes, replacement, malformed reads, permission/I/O failures, and previous-save preservation.

Exit condition:

```txt
One manual slot can be read and written atomically without risking the last valid save.
```
