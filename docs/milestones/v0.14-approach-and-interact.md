# v0.14 — Approach and interact across the demo

Status: planned; depends on accepted v0.13 navigation.
Goal: world interactions occur only after a visible player reaches a valid nearby
position; the full existing puzzle remains playable and saved progress is preserved.

## Entry conditions

- Resolve OPEN-04/05/06/07/08 in [decisions](../decisions.md).
- Retain the proven navigation model and a passing real-Pygame branch baseline.
- Confirm exact movement snapshot fields/version and tests before changing persistence.

## D140-01 — Author range and approach metadata

- [ ] Give required world targets stable references for pending action revalidation.
- [ ] Define reachable approach positions/areas and interaction radius in logical units.
- [ ] Keep click rectangles, sprite bounds, floor footprint, and reach separate.
- [ ] Add floor/blockers/spawn data for every demo scene and destination entry data for exits.
- [ ] Validate all mandatory puzzle targets and spawns against traversability.

Done when: well, witch, cup, herb, guard, inspectables, and both directions of each
exit have authored reachable behavior, including locked and completed world states.

## D140-02 — One pending approach/action

- [ ] World click in range dispatches at most one action; out of range queues travel.
- [ ] Dispatch talk, inspect, pickup, selected-item use, and exit actions only after
  successful arrival and a fresh range/reachability/world-state check.
- [ ] Keep inventory selection/combination immediate and ahead of world hit testing.
- [ ] Capture the requested target/action/item identity; never use a stale reference blindly.
- [ ] Cancel invalid requests when targets disappear, selected items change, paths fail,
  scenes change, a session loads, or confirmed modal/manual input interrupts travel.
- [ ] Do not pick up twice, consume an item early, replay an action every update, or act remotely.
- [ ] Expose approaching/unreachable feedback without revealing implementation details.

Keep transaction logic in the existing gameplay service. Range validation is a
required input/scene boundary around every player-facing world action, not duplicated
inside each rendering widget. Test both the boundary and transaction behavior.

## D140-03 — Deferred exits and scene entries

- [ ] Add one explicit scene-result/transition path for event and update completion.
- [ ] Reach the exit approach area before evaluating/performing transition.
- [ ] Preserve locked-exit feedback, item-unlock behavior, ending flags, and sound cues.
- [ ] On transition, place the actor at the exit's designated destination entry position/facing.
- [ ] Clear the old route/pending action and avoid instant return-exit retriggers.
- [ ] Preserve inventory/progression while changing position and scene.

Done when: transitions caused by walking work once and remain distinct from drawing.
Unlocking with an item and subsequently entering follow an explicitly tested policy;
preserve the existing two-action puzzle behavior unless the owner approves a change.

## D140-04 — Movement-aware saves and known legacy fallback

- [ ] Keep the outer envelope unchanged unless its own contract changes.
- [ ] Define an explicit current snapshot version with finite valid foot position/facing.
- [ ] Persist current scene and all existing inventory/quest facts.
- [ ] Load stationary; clear route, queued action, held input, open dialogue, and animation clocks.
- [ ] Read known version-1 snapshots through a narrow validation/upgrade path.
- [ ] Preserve their saved scene/progress; assign that scene's safe default spawn/facing.
- [ ] Re-saving a legacy load writes the current snapshot version.
- [ ] Reject unknown versions and malformed current-version positions safely.
- [ ] Keep the previous session and save unchanged on failed load/write.
- [ ] Test fresh, mid-walk, selected-item, changed-scene, and completed states.

Legacy fallback is accepted product behavior. It does not mean accepting missing
fields in a damaged new-format save or attempting generic migrations.

## Acceptance and non-goals

All three demo scenes use reachable grounded travel. No remote action bypasses range.
Old supported saves preserve puzzle progress at safe spawns. No camera, extra story
chain, autosave, profiles, general migration framework, or final animation art is
needed. Use placeholders until v0.15; game rules complete at the action boundary
rather than depending on a later decorative animation clip.
