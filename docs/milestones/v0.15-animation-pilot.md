# v0.15 — Player and ambient animation pilot

Status: planned; depends on accepted v0.14 movement/proximity behavior.
Goal: the visible player walks convincingly and a small scene feels alive without
changing puzzle rules or introducing a general animation engine.

## Entry conditions and art decisions

- Confirm directional/fallback policy (OPEN-09) before commissioning the full set.
- Choose one coherent original/licensed placeholder character set and record credits.
- Confirm initial clips, frame dimensions/count/rate, stable foot anchors, and asset layout.
- Choose one representative scene and one or two cosmetic loops, such as foliage,
  lantern flicker, smoke, or water. Keep important pickups visually distinguishable.
- Decide pause/focus/reset/scene-entry clock behavior explicitly before implementation.

## D150-01 — Player idle/walk presentation

- [ ] Select idle versus walk from actual movement, not merely a requested destination.
- [ ] Select facing consistently; diagonal-to-cardinal mapping is defined and stable.
- [ ] Advance clips by elapsed time and define large-delta behavior.
- [ ] Keep feet anchored across frames, turns, starts, and stops.
- [ ] Tune stride/playback against actual travel to reduce foot sliding.
- [ ] Missing clips/images have a deterministic visible fallback and cannot crash gameplay.
- [ ] Keep position/collision, pending actions, and progression independent from clip state.

## D150-02 — Depth and foreground layering

- [ ] Sort ground actors/appropriate props by authored foot/depth anchors.
- [ ] Add explicit background/foreground treatment where a tree canopy or arch cannot
  be represented correctly by one depth anchor.
- [ ] Keep UI above the world and out of world sorting/collision.
- [ ] Recheck target visibility/hit priority; an invisible required item must not remain
  an unexplained clickable target behind a foreground layer.
- [ ] Preserve navigation geometry when replacing images or changing sprite frame size.

## D150-03 — Ambient scene animation

- [ ] Implement only the chosen small loops using shared time-based playback where useful.
- [ ] Update active-scene presentation only, with an explicit pause and re-entry policy.
- [ ] Cosmetic loops never mutate flags, inventory, reachability, or interaction completion.
- [ ] Keep animation frames/clocks out of game saves; reconstruct them on load/new session.
- [ ] Preserve static fallbacks and an understandable scene when assets are unavailable.

## D150-04 — Verify visual and behavioral integration

- [ ] Automated: clip selection, elapsed-time advancement, defined loop boundaries,
  facing fallback, anchor stability, deterministic layer order, missing-asset behavior,
  and no progression mutation from ambient playback.
- [ ] Integration: move/approach/stop/interact, pause/resume, load, scene transition,
  and F11 preserve the accepted position/range/save contracts.
- [ ] Desktop: visual speed/stride, turns, foreground overlap, readable targets,
  ambient distraction, and scaling at all approved outputs.
- [ ] Full real-Pygame checks and original puzzle route remain successful.
- [ ] Record source/credit/license for every introduced asset and its replacement contract.

## Acceptance and non-goals

One complete idle/walk character set and a small ambient pilot look coherent over
the existing playable demo. Interaction success does not depend on a clip finishing.
Interaction-specific clips, full NPC schedules, cinematic tools, skeletal animation,
a universal editor, perspective resizing, and scrolling-camera work are deferred.
Only add an atlas/manifest/cache layer if the representative assets demonstrate need.
