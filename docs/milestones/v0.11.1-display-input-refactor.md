# v0.11.1 Task List — Display/Input Refactor and Hardening

Status: planned after v0.11 acceptance  
Goal: fix demonstrated display/input pressure from v0.11 while preserving gameplay and avoiding speculative architecture.

## Release-line decision

v0.11 may be completed with the current display implementation when:

- fullscreen startup and `F11` switching remain functional;
- the visible shaking/flicker occurs only during display creation or mode switching;
- the effect stops immediately after the transition;
- gameplay state, input, scene position, dialogue, and inventory remain correct;
- the issue is recorded as known v0.11.1 hardening work.

Do not treat v0.11 as accepted when the display continues shaking after the transition, switching can crash, the window becomes unusable, or gameplay state is mutated.

## Entry requirements

Do not begin implementation until:

- [ ] v0.11 automated checks pass in the real project environment.
- [ ] the full v0.11 manual regression is completed when a graphical environment is available.
- [x] fullscreen/windowed switching is functionally usable in v0.11.
- [x] mouse conversion works at the tested supported sizes.
- [x] the Controls screen displays bindings from the shared catalog.
- [x] the observed fullscreen transition issue is recorded below.

Known evidence before the audit:

```txt
- the completed v0.11 implementation visibly shakes or flickers when starting in fullscreen
- the same visible effect occurs when switching between fullscreen and windowed mode
- the issue exists before any v0.11.1 refactor is applied
- the game remains functional after the transition in the reported test
- the exact cause is not yet established
- possible causes to inspect include display recreation, temporary output-size changes,
  stale viewport geometry, or an avoidable intermediate frame
```

Initial scope expectation:

```txt
R111-02 is required because a real display-transition defect was observed.
R111-03 through R111-05 remain audit-driven and may be reduced or skipped with evidence.
Do not add a screen framework or broad display manager unless the audit demonstrates need.
```

## R111-01 — Audit the completed v0.11 implementation

No v0.11.1 source changes should be made during this task.

- [ ] Reproduce the fullscreen startup and mode-switch shaking with real Pygame.
- [ ] Confirm whether the effect is limited to the transition or continues afterward.
- [ ] Record the operating system, desktop resolution, requested display mode, returned window size, and observed behavior.
- [ ] Trace physical-window creation, logical drawing, presentation scaling, and pointer conversion.
- [ ] Trace one input event from Pygame event to semantic action to title/gameplay/ending/controls behavior.
- [ ] List duplicate calculations, duplicate raw-key checks, unclear ownership, and avoidable display recreation.
- [ ] Confirm current tests before changing code.
- [ ] Mark each remaining task below as required or skipped with a reason.

Exit condition:

```txt
The shaking/flicker is reproducible or explicitly classified as platform-specific,
and the refactor scope is evidence-based and smaller than the v0.11 feature work.
```

## R111-02 — Consolidate and harden display handling

This task is required unless R111-01 proves the visible transition is entirely external and cannot be reduced by the application.

Decision checkpoint before implementation:

- [ ] Decide whether fullscreen desktop remains a Pygame fullscreen mode at desktop resolution or uses a borderless desktop-sized window.
- [ ] Compare the alternatives in a real graphical environment before changing accepted player behavior.
- [ ] Preserve fullscreen startup, `F11`, approved windowed presets, and session-only preset memory unless a new decision is approved.

Implementation scope:

- [ ] Keep logical surface ownership, output size, scale, offset, destination rectangle, presentation, and pointer conversion in one coherent boundary.
- [ ] Use one authoritative destination rectangle for both presentation and pointer conversion.
- [ ] Give `GameApp` high-level display commands rather than duplicate scale formulas.
- [ ] Recalculate viewport geometry only after a successful display recreation.
- [ ] Avoid unnecessary repeated calls to `pygame.display.set_mode()`.
- [ ] Render and present a complete logical frame immediately after a successful mode change when practical.
- [ ] Preserve title/gameplay/controls/ending mode, current scene, dialogue, inventory selection, and all `GameSession` state.
- [ ] Leave the previous display and gameplay state intact when display recreation fails.
- [ ] Keep camera and world-space concerns out of this boundary.
- [ ] Add direct tests for viewport calculations, outside-letterbox handling, display call sequences, and state preservation.

Manual checks:

- [ ] Start directly in fullscreen and observe the transition.
- [ ] Toggle fullscreen/windowed repeatedly from title, Controls, gameplay, dialogue, and ending.
- [ ] Confirm any remaining OS transition is brief and does not produce repeated or continuous shaking.
- [ ] Confirm no intermediate incorrectly scaled or offset frame is visible where practical.
- [ ] Confirm scene targets, pointer hit testing, and game progress remain unchanged.

Exit condition:

```txt
Display creation and switching have one authoritative path, avoidable shaking/flicker
is removed or minimized, and any unavoidable platform transition is documented.
```

## R111-03 — Consolidate input actions and binding descriptions

Apply only to duplication confirmed by R111-01.

- [ ] Ensure semantic actions are defined once.
- [ ] Ensure actual key/button bindings are defined once.
- [ ] Ensure Controls-screen labels are generated from or validated against those definitions.
- [ ] Replace player-facing runtime key hints that can drift from the binding catalog.
- [ ] Remove raw menu key checks that bypass the binding catalog.
- [ ] Preserve modal priority: dialogue/menu layers consume input before lower layers.
- [ ] Add tests proving displayed bindings and accepted bindings cannot silently drift.

Skip condition:

```txt
Skip or reduce this task when the audit finds no duplicated raw bindings or drifting labels.
```

## R111-04 — Review top-level screen ownership

Decision checkpoint:

- [ ] Review `GameApp` handling for title, Controls, gameplay, and ending.
- [ ] Count duplicated event/update/draw branches.
- [ ] Decide whether the current `AppMode` design remains clearer than a small screen protocol.

When current branching remains clear:

- [ ] Keep `AppMode`; document why no abstraction was added.

When concrete duplication is present:

- [ ] Introduce the smallest screen contract that removes it.
- [ ] Do not add pause/save/load screens during this refactor.
- [ ] Do not create a reusable widget framework.

Exit condition:

```txt
Top-level presentation ownership is understandable and ready for the next menu milestone.
```

## R111-05 — Clarify display configuration ownership

Apply only when ownership is unclear after R111-02.

- [ ] Keep logical resolution separate from physical display mode.
- [ ] Keep approved preset data in one location.
- [ ] Avoid mixing user preferences with immutable game composition constants.
- [ ] Keep display choices session-only during v0.11.1.
- [ ] Defer persistence and arbitrary drag resizing to the approved settings milestone.
- [ ] Document the implemented ownership in `docs/architecture.md`.

- [ ] Verify scale/offset behavior for every supported aspect/output mode.
- [ ] Verify pointer rejection outside the logical presentation rectangle.
- [ ] Verify display toggling preserves title, gameplay, dialogue, inventory selection, current scene, Controls, and ending state.
- [ ] Verify every Controls-screen label matches an accepted input.
- [ ] Run the full demo-flow integration test.
- [ ] Run formatting, lint, and the full test suite.
- [ ] Complete the real-Pygame fullscreen/windowed transition checklist.

- [ ] Add only newly observed future refactor pressure.

Milestone acceptance:

```txt
- Fullscreen startup and mode switching no longer show avoidable shaking/flicker.
- Any unavoidable OS-level transition is brief, documented, and does not repeat.
- No display or control behavior changed unintentionally.
- Logical/physical coordinate conversion has one authoritative path.
- Input bindings and displayed controls share one source of truth where applicable.
- GameApp remains clear enough for the next pause/save/load feature.
- No speculative framework was added.
```

## Explicit non-goals

- save/load implementation
- pause menu
- editable controls
- persistent settings
- arbitrary drag resizing
- camera/world coordinates
- production asset pipeline changes
- broad class hierarchy or dependency injection rewrite
