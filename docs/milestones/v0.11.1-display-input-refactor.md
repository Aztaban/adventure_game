# v0.11.1 Task List — Display/Input Refactor and Hardening

Status: R111-03 automated implementation completed; real-Pygame transition verification remains pending
Goal: fix demonstrated display/input pressure from v0.11 while preserving gameplay and avoiding speculative architecture.

## Release-line decision

v0.11 may be completed with the current display implementation when:

- fullscreen startup and `F11` switching remain functional;
- the visible shaking/flicker occurs only during display creation or mode switching;
- the effect stops immediately after the transition;
- gameplay state, input, scene position, dialogue, and inventory remain correct;
- the issue is recorded as known v0.11.1 hardening work.

Do not treat v0.11 as accepted when the display continues shaking after the transition, switching can crash, the window becomes unusable, or gameplay state is mutated.

## Entry requirements

Do not begin implementation until:

- [ ] v0.11 automated checks pass in the real project environment.
- [ ] the full v0.11 manual regression is completed when a graphical environment is available.
- [x] fullscreen/windowed switching is functionally usable in v0.11.
- [x] mouse conversion works at the tested supported sizes.
- [x] the Controls screen displays bindings from the shared catalog.
- [x] the observed fullscreen transition issue is recorded below.

Known evidence before the audit:

```txt
- the completed v0.11 implementation visibly shakes or flickers when starting in fullscreen
- the same visible effect occurs when switching between fullscreen and windowed mode
- the issue exists before any v0.11.1 refactor is applied
- the game remains functional after the transition in the reported test
- the exact cause is not yet established
- possible causes to inspect include display recreation, temporary output-size changes,
  stale viewport geometry, or an avoidable intermediate frame
```

Initial scope expectation:

Display trace:

```txt
GameApp.__init__
-> pygame.init()
-> create one 1280 x 720 logical Surface
-> primary_desktop_size()
-> create_display_surface(desktop_size, fullscreen=True)
-> pygame.display.set_mode(desktop_size, pygame.FULLSCREEN)
-> store the returned physical display Surface
-> calculate and cache GameApp.presentation_rect from the returned size

GameApp._draw
-> clear and draw title, Controls, gameplay, ending, and debug UI to the logical Surface
-> present_logical_surface(logical_surface, screen)
-> calculate_destination_rect(...) again
-> clear unused physical output space
-> smooth-scale or directly blit the logical frame
-> pygame.display.flip()

F11 mode change
-> semantic FULLSCREEN_TOGGLE action
-> GameApp.toggle_fullscreen()
-> one create_display_surface(...) request for the target mode
-> assign the returned physical Surface only after success
-> update fullscreen/session-only preset state
-> recalculate GameApp.presentation_rect
-> normal end-of-frame draw and flip

Pointer event
-> GameApp._convert_pointer_event(...)
-> use cached GameApp.presentation_rect
-> convert_pointer_event(...)
-> physical_to_logical_position(...)
-> positions outside letterbox/pillarbox space become None
-> converted event is passed to menu, Controls, or AdventureScene hit testing
```

Input trace:

```txt
Pygame event
-> GameApp._handle_events()
-> pointer conversion when applicable
-> actions_for_event(event)
-> InputTrigger.matches(...) against the single INPUT_BINDINGS catalog

Global actions:
- F11 -> FULLSCREEN_TOGGLE -> GameApp.toggle_fullscreen()
- N -> NEW_GAME -> GameApp.start_new_game()

Mode actions:
- title/ending -> MenuScreen.handle_event() -> semantic MenuAction
- Controls -> ControlsScreen.handle_event() -> ControlsResult.BACK
- gameplay/dialogue -> SceneManager -> AdventureScene.handle_event()

MenuScreen, ControlsScreen, and AdventureScene currently translate the event again
with actions_for_event(...). This is a duplicate lightweight calculation, but it does
not duplicate binding definitions and does not currently justify a dispatcher rewrite.
```

Audit findings:

```txt
Required display pressure:
- GameApp caches presentation_rect for pointer conversion.
- present_logical_surface() independently recalculates the same rectangle every frame.
- display geometry therefore has two authoritative calculations.
- pygame.display.set_mode() is called for every requested mode change.
- set_windowed_preset() does not currently skip a request for an already-active preset.
- a mode change is not presented until the normal draw at the end of event handling,
  so a recreated display may temporarily expose an uninitialized/intermediate frame.
- the current pygame.FULLSCREEN-at-desktop-size strategy may itself cause an OS/window-
  manager transition; regular fullscreen versus borderless desktop must be compared
  with real Pygame before changing accepted behavior.

Input findings:
- no raw Pygame key checks exist outside game/input/bindings.py.
- semantic actions and physical bindings already have one catalog.
- ControlsScreen already derives its rows from that catalog.
- player-facing runtime hints still hardcode Left Click, Enter, Space, and Esc in
  MenuScreen, DialogueBox, and AdventureScene, so those labels can drift.
- repeated actions_for_event() calls are visible but are small, contextual, and not a
  demonstrated architecture defect.

Screen/configuration findings:
- AppMode branching remains short and explicit for title, Controls, gameplay, and ending.
- concrete MenuScreen and ControlsScreen objects already keep local UI behavior out of GameApp.
- no screen protocol, stack, general UI framework, display manager, or settings repository
  is justified by the current implementation.
- logical resolution and approved presets already live in one settings module; session-only
  display state remains in GameApp and persistence is correctly deferred.
```

## R111-02 — Consolidate and harden display handling

Classification: **required**. The audit found duplicate viewport authority, an observed real transition defect, and a possible intermediate-frame/display-recreation issue. The fullscreen strategy still requires a real-Pygame decision checkpoint.

Decision checkpoint before implementation:

- [x] Preserve Pygame fullscreen mode at the primary desktop resolution during this refactor. Borderless desktop fullscreen is not adopted without a real graphical comparison.
- [ ] Compare regular fullscreen and borderless desktop alternatives in a real graphical environment before any later player-visible strategy change.
- [x] Preserve fullscreen startup, `F11`, approved windowed presets, and session-only preset memory.

Implementation scope:

- [x] Keep logical surface ownership, output size, scale, offset, destination rectangle, presentation, and pointer conversion in one coherent `DisplayViewport` boundary.
- [x] Use one authoritative destination rectangle for both presentation and pointer conversion.
- [x] Give `GameApp` high-level viewport commands rather than duplicate scale formulas.
- [x] Recalculate viewport geometry only after a successful display recreation.
- [x] Avoid unnecessary repeated calls to `pygame.display.set_mode()` when the requested mode and size are already active.
- [x] Render and present a complete logical frame immediately after startup initialization and every successful mode change.
- [x] Preserve title/gameplay/Controls/ending mode, current scene, dialogue, inventory selection, and all `GameSession` state.
- [x] Leave the previous viewport references and gameplay state intact when display recreation fails.
- [x] Keep camera and world-space concerns out of this boundary.
- [x] Add direct tests for viewport calculations, outside-letterbox handling, display call sequences, no-op mode requests, immediate redraw, and state preservation.

Implemented facts:

```txt
- DisplayViewport owns the 1280 x 720 logical surface, active physical surface,
  destination rectangle, uniform presentation, display flip, and pointer conversion.
- Presentation and pointer conversion use the same stored destination rectangle.
- GameApp owns only high-level mode choice and session-only fullscreen/preset state.
- Re-selecting the active windowed preset returns successfully without recreating the display.
- Successful display recreation commits new viewport geometry and immediately draws the
  current title, Controls, gameplay, dialogue, or ending frame.
- Failed recreation does not commit new viewport geometry or mutate the game session.
- The accepted pygame.FULLSCREEN-at-desktop-resolution strategy remains unchanged pending
  a later real-Pygame comparison with borderless desktop behavior.
```
